# Project Configuration

These settings correspond to the `configuration` block in
`.ai/rules/universal-engineering-ruleset.json`. Keep the two in step.

## Required Project Values

- `project_name`: `arbiter`
- `repository_type`: `application` (Python CLI and library, package `arbiter-eval`)
- `primary_language_or_stack`: `Python >=3.11`, setuptools with a `src/` layout; the only runtime dependency is `PyYAML`; optional `ast` extra adds tree-sitter
- `package_manager`: `pip` (`pip install -e .[dev]`; external analyzers via `./tools/install_tools.sh`)
- `build_command`: `pip install -e .`
- `test_command`: `python -m pytest -q -rs -m "not slow"` (the fast tier, the gate's suite); `python -m pytest -q -rs -m slow` runs the analyzer-backed tier once `./tools/install_tools.sh` has run (ARB-046) — the golden-fixture tests over `fixtures/legacy-platform` are the ones that matter; a rule or adapter change that misses a planted defect fails the suite. `python tools/integrity.py` and `python tools/mutate_tests.py` run in CI alongside it, then `python omni doctor` and `python omni gate`
- `lint_command`: none gating; `ruff` is available through the `tools` extra
- `typecheck_command`: none configured
- `changelog_location`: `CHANGELOG.md`, grouped by date under `[Unreleased]`, each entry citing its `REQ-###`
- `documentation_locations`: `.ai/project-context.md` (decision history), `CHANGELOG.md`, `README.md` (overview: capabilities, administration, versioning, licensing), `docs/` (granular reference, one file per category), `SETUP.md` (installation), `NOTICE.md` (third-party components), `docs/licensing.md` (Apache-2.0 decision, third-party obligations, open licensing questions), `.ai/failures/failure-ledger.json` (shipped defects, via `python omni failure`)
- `branching_or_pr_standard`: main branch `main`; remote `github.com/paukennick/arbiter`; no PR template in-repo
- `comment_style`: minimal — comments only for non-obvious WHY, matching the existing `src/arbiter/` style
- `requirement_id_prefix`: `REQ` — active registry at
  `.ai/requirements/requirements.json`, retired entries at
  `.ai/requirements/requirements-archive.json`; never read or hand-edit
  either. Query with `python omni requirement show|list|search`, assign the
  next free ID with `python omni requirement add` or `draft` (both allocate
  across the two files so a retired id is never reused), close with
  `python omni requirement complete`, and sweep terminal entries out with
  `python omni requirement archive`

## Project-Specific Notes (arbiter)

- `CLAUDE.md` is a thin routing shim to `.ai/entrypoints/claude.md`. Claude
  Code is the assistant used here, but since 2026-10-09 (ARB-031) the other
  shims (`AGENTS.md`, `.cursorrules`, `.cursorignore`, `LLM_CONTEXT.md`,
  `.github/copilot-instructions.md`, `.kiro/steering/omnicontext.md`) are
  installed too; they are generated by `python omni sync` and all route to the
  same `.ai/` source of truth.
- The OmniEngineering CLI is at the repo root (`omni`, `make_ai.py`,
  `omni_graph.py`, `omni_mcp.py`): run `python omni doctor`, `python omni map`
  (regenerates `.ai/project-map.md`; safe here because the map is not
  hand-curated), `python omni sync`, and `python omni gate`. The workspace is
  tracked against the upstream OmniEngineering checkout in
  `.ai/omni-version.json`; pull later template changes with
  `python omni update --source ../OmniEngineering` (3-way merge, arbiter's own
  edits preserved).
- **Enforcement.** `.githooks/pre-commit` runs `python omni gate` and
  `.githooks/post-commit` rebuilds the code graph in the background; a fresh
  clone opts in with `git config core.hooksPath .githooks` (or
  `python omni hook install-git --with-graph-rebuild`). `.claude/settings.json`
  (tracked) carries the Claude Code Stop hook that blocks a session from
  finishing while the gate fails. `.github/workflows/pr-check.yml` runs
  `python omni doctor` and `python omni gate` on every pull request. The gate's
  `co_changed` rules exempt `training/**` and `.arbiter/**`, because the
  nightly `train.yml` job commits measurement output there with no
  requirement of its own, by design (ARB-023). Its `data.privacy` secret
  check exempts `tests/**`, `fixtures/**` and `examples/**`: Arbiter is a
  secret scanner, so planted keys and the example AWS key from the AWS
  documentation are its test material, not leaks (see `NOTICE.md`). No file
  under `src/` or `tools/` holds a literal key shape, and all of them stay
  scanned.
- **Code graph.** `python omni graph build` writes `.ai/project-graph.json`
  (git-ignored; needs `tree-sitter` plus a python grammar: either the
  `tree-sitter-python` wheel or `tree-sitter-language-pack`, which Arbiter's
  own `ast` extra installs and the graph falls back to). `.ai/graph-config.json`
  excludes `fixtures/`, `examples/`, `training/`, `.arbiter/`, `arbiter-out/`
  and `arbiter-ab/` from the code layer: fixtures are planted-defect corpora,
  not arbiter's source, and a graph that linked them would attribute their
  symbols to the product. A finding raised on an excluded path still gets a
  plain `file` node (no symbols) so it stays traceable. `.ai/test-suites.json`
  registers the pytest fast tier (`root-pytest`, the gate's suite), the slow
  tier (`root-pytest-slow`, integration, run by CI's slow-tier job) and
  `tools/check_writeback.sh`.
- **Findings in the graph (ARB-064).** Every unsuppressed Arbiter finding is a
  `finding` node in the assurance layer, with `rule_id`, `probe`, `dimension`,
  `severity`, `status`, `tags`, `cwe` (list), `controls` (list) and `sources`
  (the report(s) it came from). Its edges: `flags` the file and the smallest
  enclosing function/class, `violates` its `arbiter_rule` node (attrs `probe`,
  `title`), `classified_as` each `cwe` node (named from a built-in CWE table;
  the rule is `classified_as` the same CWEs), `cites` the requirement named by
  a `req:<ID>` tag, `recorded_as` the ledger failure whose `how_detected` names
  it, and `introduced_by` the commit git blame holds for its line.
  - *Which reports.* With `findings_report: "auto"` (the default) the graph
    reads two: the newest **full** report under `arbiter-out/` (any
    `report.json` whose `scan_scope.mode` is not `partial`) as the base, and
    the newest **partial** report under the gate rule's `--out` directory
    (`arbiter-out/omni-gate/`) on top. Findings are deduplicated by `id`; the
    newer report wins on `status`. `findings_report: "<path>"` reads exactly
    that one report; `null` disables finding nodes.
  - *Keeping it current.* `./omni graph build --if-stale` is a no-op unless
    HEAD, a report, a requirement registry, the failure ledger or the suite
    file moved since the graph was written (the graph records them under
    `inputs`). `./omni gate` calls it when a graph file already exists and
    prints one advisory `graph: ...` line; a rebuild failure never fails the
    gate. A workspace whose `make scan` runs `arbiter scan` should chain the
    same call: `arbiter scan . --out arbiter-out && ./omni graph build --if-stale`
    (and set `findings_report` to that report path when its `arbiter-out/`
    layout differs from the default).
  - *Asking.* `./omni graph findings --cwe CWE-362`, `--rule 'arbiter/concurrency.*'`
    (glob or substring), `--under src/`, `--dimension`, `--severity`;
    `./omni graph why f:<id>` (rule, CWE, flagged code, requirement, commit),
    `./omni graph why CWE-89` (every finding and file of that class),
    `./omni graph impact src/x.py` (a `findings` bucket) and
    `./omni graph impact CWE-89` (its findings and their files);
    `./omni graph show --all --kind cwe|arbiter_rule|finding`. Over MCP:
    `graph_findings` (same filters), `graph_cwe` (one CWE or rule id) and
    `graph_impact` (with `paths`). End to end:

    ```
    arbiter scan fixtures/planted/python/bad --profile offline --out arbiter-out/full
    ./omni graph build --if-stale
    ./omni graph findings --cwe CWE-362
    ./omni graph why f:d6ac7c224062
    ```
- **Failure ledger.** `.ai/failures/failure-ledger.json` records every shipped
  defect with its root cause, regression test and prevention rule; it was
  backfilled from `CHANGELOG.md` and `.ai/project-context.md` on 2026-10-09.
  `python omni requirement complete` refuses a requirement whose category
  matches defect/bug/fix/regression without an entry; arbiter's categories
  (`developer-tooling`, `documentation`, `training-evidence`, `legal`) do not
  trigger that check, so record defects deliberately rather than relying on
  it, or file defect work under a `defect` category.
- **`.mcp.json` registers two MCP servers.** `arbiter` runs Arbiter's own
  server (`arbiter mcp`, stdio, tools `arbiter_scan`, `arbiter_gate`,
  `arbiter_review_queue` — see `docs/mcp.md`). When those tools are available,
  call Arbiter through them instead of shelling out to the `arbiter` CLI —
  same `src/arbiter/service.py` underneath, no `Bash` permission prompt, and
  the result comes back as structured JSON rather than text to reparse. The
  CLI is still the right choice for anything the tool surface deliberately
  omits, chiefly `arbiter review --apply`: no MCP tool records a verdict (see
  `mcp.py`'s module docstring). `omni` runs `python omni mcp serve`, the
  read-only graph, requirement, failure and gate tools from `omni_mcp.py`.
  `python omni doctor` starts both servers for real and takes them through
  `initialize` and `tools/list` (upstream's generic check, which replaced the
  arbiter-only `validate_mcp_server` from ARB-025), because the `mcp` SDK's own
  shape has moved under this project before and a static read of `.mcp.json`
  would not have caught it. `arbiter mcp` needs the `mcp` extra installed.
- **History of the scaffold (ARB-001, ARB-028, ARB-031).** The workspace was
  first assembled from local STEP-Migration copies because no OmniEngineering
  upstream was on that machine, and `.ai/adapters/*`, `.ai/checklists/public-
  release.md`, `.ai/rules/fallback-llm-rules.json` and
  `.ai/rules/hci-ui-rules.json` were authored directly for arbiter on
  2026-09-17. On 2026-10-09 the workspace was re-synced to the real upstream;
  the arbiter-authored files were kept (3-way merged where upstream had moved)
  and remain arbiter-specific content. `python omni doctor` now reports no
  errors; its remaining WARNs are the ruleset's own requirement-template
  placeholders, the README not referencing OmniEngineering's architecture SVG
  (presentation assets were not adopted), the optional `omni` console script,
  and training-run commits that postdate the last CHANGELOG entry (expected:
  they carry no requirement). Any FAIL is real drift.
- **CI.** Two workflows. `.github/workflows/pr-check.yml` runs on every pull
  request over a matrix of `ubuntu-latest` and `windows-latest` — the fast
  tier of the suite with `-rs`, then `tools/integrity.py`, the mutation
  check, doctor and gate — plus a parallel Linux `slow-tier` job that
  installs the analyzers and runs `-m slow` (ARB-046). `.github/workflows/train.yml` runs the two-hour measurement cycle
  nightly on ubuntu only and commits its results back. The matrix is on the
  fast workflow deliberately (ARB-024); `fail-fast: false` so a Linux failure
  cannot cancel the Windows job. Neither is a *required* check: this repository
  has no rulesets and `main` is unprotected, so both are informative until that
  changes.
- **Headroom** is installed at local scope in `.claude/settings.local.json`
  (git-ignored): `ANTHROPIC_BASE_URL=http://127.0.0.1:8787` plus
  SessionStart/PreToolUse hooks that run `headroom init hook ensure` to keep
  the proxy up. The `headroom` MCP server (`headroom_retrieve`,
  `headroom_compress`, `headroom_stats`) is registered at user scope. To
  remove the integration: `headroom unwrap claude` or delete that file.
- Arbiter's own rules apply to work on it: coverage is reported, never
  assumed; the tool never executes the target; deterministic and inferred
  findings never blend. See `README.md` "Principles" (six, not four — the
  count grew when knowledge pinning and machine-checked invariants landed).
